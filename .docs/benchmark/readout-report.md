# Archway Benchmark Readout Report (전체 시나리오)

## 1. 목적
- Gateway + Gateway-Controller의 **100k RPS 내부 운영 가능성**을 재판정한다.
- gRPC를 고려한 이유는 **지연시간 단축 자체보다 처리량(throughput) 확대**이며, HTTP/1.1 대비 **멀티플렉싱(multiplexing)**으로 동시 요청 처리 효율을 높이기 위함이다.
- 본 문서는 `.docs/benchmark/자료/`에 있는 최신 산출물 기준으로, **이번 사이클에서 실행한 시나리오를 전부** 포함한다.
- 본 문서에서 E2E 정의는 **Gateway → Gateway-Controller → Upstream 전체 경로**를 의미한다.

## 2. 측정 조건
- 환경: `darwin/arm64`, `Apple M4`
- 공통: `go test -bench`, `-benchmem`, `-benchtime=1s`, `-count=1`
- 포함 범위:
  1. Gateway middleware matrix 전체
  2. Gateway 파이프라인 벤치(matrix) 전체
  3. Controller gRPC listener(unix/tcp) 전체
  4. Controller unix HTTP 전체
  5. Controller 처리량 병렬 벤치(gRPC vs HTTP) 전체
  6. Gateway full-chain E2E (Gateway → Gateway-Controller → Upstream, rewrite 포함)

## 8. 결론
- gRPC 채택 의도(멀티플렉싱 기반 처리량 향상)는 병렬 처리량 벤치에서 대부분 시나리오에서 확인된다.
- 사용자 정의 E2E( Gateway → Gateway-Controller → Upstream, rewrite 포함 )는 본 문서 7장에 별도 반영했다.
- 지표 해석 요약:
  - **p50**은 평시 체감 속도, **p95**는 운영 기준, **p99**는 피크/꼬리 지연의 안전성 지표다.
  - **ns/op**는 더 낮을수록 좋고, **B/op / allocs/op**는 GC 압박과 RSS 성장에 직접 영향을 준다.
  - 이번 결과는 full-chain에서 gRPC가 처리량 우위를 유지하면서도 메모리 비용이 과도하게 폭증하지 않는다는 점을 보여준다.
